> Profile scope: default reading tasks follow [practical](practical.md). The strict/low-level details below are consulted as needed, not requirements to exhaust warnings, formula reviews or independent rebuilding in ordinary tasks. Actual viewing evidence remains required.

# Recovery state and review lifecycle

## Version 3: in-place source inventory

The default extract/build interface and complete block fields are in [inplace.md](inplace.md). v3 retains source SHA-256/page count, exact visible geometry, immutable glyph facts, stable block IDs, selected glyph ranges, translation/method, allowed and actual boxes, and actual font runs. Use replace, cover, preserve or unresolved explicitly. Keep source numerical/formula glyphs in preserve blocks; do not mark an entire mixed sentence preserve merely to avoid layout work.

check-state re-extracts source glyphs and validates geometry, glyph ownership/ranges, method constraints, allowed/actual boxes and source identity. Native hidden OCR cannot be replaced without covering the visible scan. Source glyph facts must never be edited to suppress an error. Drawing-time checks additionally validate overflow, missing glyphs, selected masking and real-text collisions. Image/outline inventory and the semantic safety of a cover still need visible review.

v3 draft states can cover a selected page subset and map it consecutively to a trial PDF. Full --final checks still require every original page and all review evidence. preserve blocks reuse existing text and are excluded from new font-run coverage. Newly drawn blocks and optional generated page labels must match actual run text. Metadata alone does not prove that the glyphs rendered correctly.

## Format and coordinates

Use UTF-8 without BOM JSON. New tasks use schema_version 3, generated by [inplace.md](inplace.md); versions 1 and 2 remain readable for historical packages. The v2 example below documents the explicit legacy builder and the shared evidence lifecycle, not the default layout. Paths resolve relative to state.json unless absolute. In the default layout, current state is in <source-stem>/recovery/; source.path and published output.path normally point two levels up to the sibling PDFs, while review evidence stays inside the working folder. Hashes are lowercase SHA-256 of actual bytes. The following one-page example illustrates fields; placeholder hashes must be replaced, and it does not claim final review.

~~~json
{
  "schema_version": 2,
  "document": {"source_kind": "english-original"},
  "source": {
    "path": "original.pdf",
    "sha256": "<actual SHA-256>"
  },
  "output": {
    "path": "bilingual.pdf",
    "sha256": "<actual SHA-256>"
  },
  "layout": {
    "builder": {
      "path": "build.py",
      "sha256": "<actual SHA-256>"
    },
    "fonts": [
      {
        "name": "Chosen font",
        "sha256": "<actual font SHA-256>",
        "source": "Permitted local/source location",
        "purpose": "Chinese regular text"
      }
    ],
    "pane_width_pt": 240,
    "body_size_pt": 10
  },
  "glossary": [
    {
      "source": "opening hours",
      "target": "开放时间",
      "context": "visitor information"
    }
  ],
  "pages": [
    {
      "source_page": 1,
      "output_page": 1,
      "source_rect": [
        0,
        0,
        240,
        300
      ],
      "kind": "translated",
      "inventory_reviewed": true,
      "expected_blocks": [
        "p001-body01"
      ],
      "reading_order": ["p001-body01"],
      "context_reviewed": false,
      "blocks": [
        {
          "id": "p001-body01",
          "kind": "paragraph",
          "source_bbox": [
            20,
            30,
            220,
            70
          ],
          "target_bbox": [
            260,
            30,
            460,
            80
          ],
          "source_text": "The reading room opens at 9 a.m.",
          "translation": "阅览室上午 9 点开放。",
          "status": "translated"
        }
      ]
    }
  ],
  "issues": [],
  "qc": {}
}
~~~

source_rect is the original pane rectangle in the output's visible top-left coordinate system, in PDF points. It must match the original visible dimensions at 1:1 scale. source_bbox uses the source visible top-left system. target_bbox uses the output visible top-left system. Rotation and crop are already accounted for in these coordinates; raw PDF bottom-left coordinates must be converted. All page numbers are one-based.

## Equal panes and display page labels

Source W × H visible dimensions determine both panes per page; output is 2W × H and source_rect is [0,0,W,H]. Omit the legacy layout.pane_width_pt for mixed widths; when present it must match each source width. Keep actual block font_size, leading, target_bbox and reflow reasons in state so rebuilding reproduces local fitting.

Record the agent-confirmed document numbering policy as layout.pagination_strategy: preserve-source or physical-total. When supplied, every page has pagination with source_label (the visible original string, or null) and text (the displayed string, or an empty string for an unnumbered page). Preserve-source requires text to equal source_label, leaving unlabeled covers blank. Physical-total requires no source labels and text equal to the one-based physical source_page followed by / and the total input page count. Visible Roman/section labels never replace physical indices. Keep unreadable-source concerns in issues; the checker cannot verify the agent's identification.

A nonempty page label also has a unique id, target_bbox in output visible top-left points, font_size and optional registered font. For example, page 1 of a wholly unnumbered three-page document can use pagination: {"id":"p001-page-number","source_label":null,"text":"1/3","target_bbox":[420,10,460,25],"font_size":8}. Confirm this box against the actual page and reserve it before layout. Page labels are separate from source semantic blocks and expected_blocks; never duplicate an original page number in both places. The builder/font checker includes their IDs and actual font runs. Bounds and collisions still need final visual review.

These optional records use the current schema and are included in layout/page fingerprints, so changing labels, positions or font sizes invalidates earlier reviews. Historical states without them remain readable and do not acquire a fabricated numbering check. A fresh audit applies current equal-pane rules while preserving old records.

## Block and page records

Every original page must appear once, and every output page maps once. expected_blocks is the independently reviewed source inventory; blocks must contain exactly these IDs, unique throughout the document. Use kinds such as heading, paragraph, list-item, table, formula, caption and figure-label.

A block keeps source_text and a nonempty translation. status is translated, verbatim or pending. verbatim requires reason and the retained text as translation. pending is a draft warning and final error. A page with no translatable material uses kind no-translation-needed plus reason; do not use this to skip untranslated text.

A table block additionally requires table.source_rows and table.translated_rows: arrays of rows of strings, with the same cell counts per corresponding row. Nonempty source cells need nonempty target cells. Preserve merged-cell spans, header roles and footnote anchors in extra table metadata. caption and figure-label require figure_id. Optional target_bbox validates the declared destination rectangle; it does not prove where the builder actually drew text.

Keep context, original expressions, reading order and anchors as additional fields where useful. Layout includes a SHA-bound builder and a font registry (name, sha256, source and purpose) for final readiness. Optional layout.inputs is a list of {path, sha256} records for external layout/translation data; declared files are checked against disk and changes invalidate the state. Builder contents are checked against disk; font records are required metadata, not proof that those fonts were embedded or are currently installed.

## Content fingerprint and invalidation

The content fingerprint hashes source, layout, glossary, pages and issues using sorted-key UTF-8 JSON with compact separators. Use the helper directly rather than reproducing the serialization:

~~~python
import sys
sys.path.insert(0, "<skill-dir>/scripts")
import pdf_tools
state = pdf_tools.read_json("state.json")
fingerprint = pdf_tools.content_hash(state)
~~~

output and qc are excluded from that fingerprint to avoid a circular hash. They have separate byte fingerprints. Any edit to translation, mapping, glossary, layout, issues, source or builder invalidates prior acceptance. For a new build, clear qc, update source/output/builder hashes, run draft check-state and rebuild as necessary. Do not “repair” a stale review just by replacing hashes.

## Final review record

After final saving, subsetting and cleanup, audit the exact delivery file and render every page. Actually inspect each page and perform semantic checks before recording reviewed page lists. Then populate qc:

~~~json
{
  "content_sha256": "<pdf_tools.content_hash(state)>",
  "source_sha256": "<actual original SHA-256>",
  "output_sha256": "<actual final PDF SHA-256>",
  "translation_pages": [1],
  "visual_pages": [1],
  "reviewer": "<actual reviewer/session>",
  "reviewed_at": "<ISO 8601 with timezone>",
  "structure": "passed",
  "audit_path": "audit.json",
  "structure_notes": "<specific warning resolutions, or no warnings>"
}
~~~

For final readiness, audit must mechanically pass and match the actual source/output hashes. Warning explanations are required when warnings exist. issues must be resolved, or retained with a note that explains the preserved uncertainty and what the user needs to know. Retained issues are disclosed, not silently treated as accurate translation.

The final check requires both page lists to cover every source page exactly, the reviewer/time, valid builder metadata, output fingerprint and audit. It checks consistency of recorded attestations, not their truth: do not create acceptance records from mere rendering or passing tests. A synthetic test may exercise accepted-state validation with explicitly labeled fixture attestations; it is not a real document review.

## Recovery and failure handling

check-state without --final validates draft consistency. Missing files, changed source/output/builder bytes, incomplete inventories or stale nonempty qc are errors. Finish pending blocks and inventory review before --final. Inspect JSON errors by code/page/block, correct the underlying cause and rerun.

Save state after completed batches and keep the builder beside it. On resume, verify source hash first, then restore glossary, translations, mappings and layout decisions. Do not extract the previous Chinese PDF and treat it as the authoritative recovery source. Keep disposable renders outside the compact recovery package.


## Version 2: actual review evidence

Versions 2 and 3 use the page-bound evidence below; the legacy example above is only a draft. Add document.source_kind (original for other source languages, english-original, official-chinese, or generated-translation), vendor and naming evidence as applicable. Every page's reading_order must equal its ordered blocks IDs. Record context_pages and context_reviewed:true only after checking semantic dependencies; otherwise the fingerprint conservatively includes the whole book. Layout, glossary and issues are always dependencies. Issues affecting meaning include page, block, source_quote, concern and treatment; an optional suggested_correction needs evidence. Keep the original expression near the translated note.

Run the builder, check-fonts, audit and full render on a frozen candidate before review. The output state must reference the frozen output and actual builder inputs. Use a new render directory for a new version; do not overwrite an index already cited by a review. The render index includes exact output/source fingerprints, renderer version/settings, PNG file hash, RGB pixel hash, and page_content_sha256. Changing PNG metadata alone does not change the pixel hash, but the current file hash still has to match its own current index.

In addition to the version 1 qc fields, version 2 requires font_assignments (path to the actual run report), font_report {path, sha256}, and page_reviews covering every source page. A viewed record has:

~~~json
{
  "page": 1,
  "mode": "viewed",
  "output_sha256": "<actual PDF hash>",
  "render_index": {"path": "../work/render-v1/index.json", "sha256": "<actual index hash>"},
  "settings_sha256": "<index settings hash>",
  "image_sha256": "<page PNG file hash>",
  "pixel_sha256": "<rendered RGB pixel hash>",
  "page_content_sha256": "<index content hash>",
  "reviewer": "<actual session/reviewer>",
  "reviewed_at": "<ISO timestamp with timezone>",
  "evidence": "<actual image-open tool event or review notes reference>"
}
~~~

Record mode viewed only after opening that full page and doing the checks. For mode reused, retain the current render's hashes and add previous (the original complete viewed record) and reuse_reason. Both render indices and image files must remain available. Only identical settings, pixels and semantic dependency fingerprints allow reuse. Changes to glossary, shared layout, issues or relevant context invalidate it. Reuse is a consistency check, not proof that an earlier observer understood the page; no tool automatically fills review attestations.

The v2 content fingerprint additionally includes document. check-state --final rechecks actual font assignments, font file hashes, render evidence and source/output bindings. It reports mechanical_checks_passed, review_evidence_level and quality_certified:false. The old ready_for_delivery field remains for compatibility and cannot certify translation. Version 1 reports legacy-attestation-v1; do not add invented v2 evidence when migrating old work.

## Publishing and optional working-folder cleanup

Publishing a byte-identical accepted candidate to the outer delivery path only changes current output.path; output and qc are excluded from the content fingerprint. Retain hashes and original review records, and rerun final consistency checks at the delivery path as described in [building.md](building.md). This is not a source rename or a new review. Changes to fingerprinted source/layout paths still follow the relocation or invalidation rules below.

Keep all recovery, reports and review evidence inside the same-stem working folder. The user may delete this folder after review while retaining the two independent PDFs. Such deletion intentionally removes recovery state and evidence: later check-state, evidence reuse and state-driven rebuilding are no longer available from that package. Do not claim those checks still pass, reconstruct lost acceptance from the PDFs, or automatically delete the folder.

## Path-only relocation

Before an approved rename, copy the original state bytes to a historical snapshot and preserve its qc unchanged. Update only current source/output paths. Add migration with kind:path-only, performed_at, reason, previous_state:{path,sha256}, old_source and new_source. Keep original audit/review reports. The validator verifies the historical content fingerprint, identical qc, unchanged PDF fingerprints and content equality after reversing only source.path. It then emits verified_path_only_migration instead of stale_qc_content; this preserves an old acceptance, not a new review. Builder/translation/layout edits cannot use this exception. Other metadata changes use ordinary invalidation; regeneration tests run in independent copies.

Successive renames retain a snapshot before each hop. The validator follows every hash-bound previous_state until an original acceptance is reached, checking identical qc, PDF fingerprints and content after reversing only source.path at each hop. It rejects missing or modified snapshots, cycles and content/layout changes, even when the latest path happens to equal the initially accepted path. Existing single-hop records remain readable.

By default, references inside a historical snapshot resolve from its containing directory. If a byte-for-byte snapshot was moved into history/ while its references were originally relative to the task recovery directory, add previous_state.base_path to the new migration record; it is resolved relative to the referencing state's base. For example, previous_state:{path:'history/before-second-rename.json',sha256:'<actual SHA-256>',base_path:'.'} preserves the previous snapshot's original recovery-directory context. Never rewrite the snapshot to repair its links. Historical evidence remains historical; keep additional naming information in the task migration manifest and do not edit content fingerprints or reviewer attestations.
