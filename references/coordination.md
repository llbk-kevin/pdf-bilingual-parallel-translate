# Coordinating translation and independent review

## Dispatch and host setup

Every PDF gets translation and fresh-context independent review, including a short document. The coordinator uses the current session model. Suggest Luna xhigh, subject to user choice, and explicitly pass model='gpt-6-luna', reasoning_effort='xhigh', fork_turns='none' when that choice is confirmed. New page translators also receive fresh contexts and compact packages, not the coordinator's discussion history. Resume original workers for repairs from their checkpoints.

At the first naming confirmation, or in the proposed execution plan, show an agent work table beside the exact filename table. Include stable task name, document/physical pages, translation/review/merge duties, model and effort, context mode, dependencies and handoff location. Identify one state writer per document; a translator can own merging without a separate relay-only coordinator. Long-document boundaries can be provisional until preflight. For example, task ID d02_translate_p001_018 can display as "D02 Handbook | Translate 001–018". Use these names on resume rather than creating a new fix/finish/resume agent each round.

Check the requested model with one minimal, non-PDF probe before productive dispatch, and reuse availability evidence for the same host/account/model/effort. A missing static catalog entry means unverified, not unavailable. Save requested parameters and available host/tool evidence for each actual agent; neither the probe nor an agent's self-description verifies a different work agent. If its actual model/effort cannot be observed, leave actual values unclaimed and label them unverified. On a real error or mismatch save the queue and ask before choosing another model; never silently inherit or substitute the parent model. Recheck availability after host/account changes or a real error, not before every page task.

Missing per-agent metadata alone does not block work with explicit confirmed arguments after the availability probe succeeds. Do not add a startup probe or a coordinator waiting gate for every worker; collect available identity-bound evidence without inventing new mandatory stages.

Check actual subagent tools and read host settings with scripts/coordination.py --config <CODEX_HOME>/config.toml. An unset agents.max_concurrent_threads_per_session uses the host default. On first use with no explicit setting, or when capacity affects dispatch, explain the current situation and ask whether the user wants a specific change. Record the choice in work/coordination.json. Existing capacity can run queued work while this optional choice is pending. Write a setting only after approval of its exact value. After a change, save a checkpoint, remind the user to fully quit and restart Codex, and verify actual tool availability after restart. Configured capacity alone does not establish effective capacity.

Follow [naming.md](naming.md) and confirm both tables before prepare and productive dispatch. Resume recorded choices without asking again. The coordinator may adjust page boundaries and add justified parallel assignments, recording and reporting why; unapproved model/name/destination changes need confirmation. Document owners propose additions to the coordinator rather than spawning outside the ledger. Give workers confirmed paths, frozen command_prefix/runner, page ownership and compact inventory. Adjacent pages are read-only context; keep continued sentences/tables together before placing each part on its page.

## Dynamic scheduling

Dispatch executable tasks using available slots and memory, without a fixed agent count or role allocation. Reviews become ready after machine checks. Prefer original translators for repairs and original reviewers for rechecks; add workers for independent parallel work, an unavailable original worker or a different expert judgment. Save queued work and use bounded waits. Existing jobs can finish; low memory queues new heavy work rather than freezing lightweight edits and viewing already-rendered pages. Report meaningful changes, not an unchanged waiting loop. A reply ending does not leave an agent queue running automatically. User-requested phase ordering and resource instructions take precedence.

Store the confirmed work table and dispatch history in work/coordination.json using the contract below. ready_tasks(tasks, available_slots, memory=None, reserve_bytes=None, check_memory=True) prefers ready reviews without reserving slots. System reserve defaults to max(2 GiB, 10% of physical RAM). Task work/resource-settings.json can override memory_reserve_bytes; memory_checks_enabled=false records an explicit task override. Pass these settings as reserve_bytes and check_memory to ready_tasks. resource_class='light' allows genuinely lightweight work while heavy tasks wait; default is heavy. estimated_memory_bytes defaults to 256 MiB until measured. This system reserve differs from the unchanged local Python worker lease/estimation algorithm. Host tools perform spawning and waiting.

## Work-plan contract and validation

Run `python scripts/coordination.py validate-plan --plan TASK/work/coordination.json` before dispatch and after assignment changes. It is read-only, returns ok/errors, model checks and a summary; invalid plans exit 1. It validates structure, not user authorization, model availability or semantic quality.

- documents: id, selected physical pages as a positive integer list, and state_writer referencing a translation/repair task. The writer may have owns_edits=false when page translators own the edits.
- tasks: unique id and display name; document; pages; phase (translate/review/repair); explicit owns_edits; model; reasoning_effort; fork_turns; responsibilities; handoff; depends_on task IDs; status (queued/running/completed/blocked). Translation and review tasks require fork_turns='none'. Read-only context pages are not editing pages. Translation owners and review tasks must cover the selection; active edit ownership cannot overlap. A repair task reassigns pages only after the previous owner completes or transfers ownership. Review dependencies must transitively include the relevant translators.
- tasks may record agent_id, artifacts, resource_class, estimated_memory_bytes and resume_count (default 0). Increment resume_count when continuing the same agent; do not add another launch for a follow-up.
- launches is append-only: task, unique actual agent_id, requested_model, requested_effort, optional actual_model/actual_effort, host/tool evidence and evidence_agent_id. Failed calls without an agent ID are diagnostics, not launches. No model substitution is allowed; mismatched values or an error block validation. Actual values are verified only when evidence_agent_id matches this launch's agent_id and evidence names its host/tool record. Missing or probe-only evidence is unverified. model_checks stores probe evidence objects with agent_id when created, host/account scope and availability result.

For a short two-page PDF, use one translate task owning pages [1,2] and one review task depending on it, with that translate task as state_writer. For a split document, the writer's translation task can depend on page translators before review becomes ready. A queued/running review also depends on overlapping pending repairs; feedback is an artifact, not a circular dependency from repair back to that same review task. Reviewers submit observations for serial registration by the writer. The same agent cannot translate/repair and independently review its document, including past launch identities. A new reviewer receives source, renders, criteria and an empty template, not the translator's verdict.

The summary distinguishes unique created_agents (work and recorded probes), work_agents, probe_agents, currently running work agent IDs, queued/blocked tasks and total resume_count. It is based on recorded identities, never call counts, process counts or UI totals. Do not label cumulative created agents as a concurrency peak.

Each document state has one writer at a time. Different documents can update concurrently. Reviewers submit real observations; the assigned document writer registers them and merges accepted patches. The coordinator owns overall decisions and publication.

## Packages and recovery

Export coherent ranges with pipeline package --state recovery/state.json --pages RANGE --out work/packages/PACKAGE --owner AGENT_ID. Each package contains editable state, compact inventory, a baseline and read-only adjacent context. Workers save edits.json, apply and preview locally. The document writer applies the patch with its package manifest. Replayed patch fingerprints are idempotent; baseline conflicts return only affected pages.

Use status with active packages and candidate states for progress. Keep actual agent IDs, committed paths, unfinished pages and blockers on disk. Resume an available original worker or give a new worker the remaining assignment from this checkpoint. Review reuse requires matching page evidence and dependencies.

Use verify's existing review_handoff and observations_template; do not manually recreate their bundle. Save clear-page observations before repairs, then use --previous-state. A worker handoff needs paths, blockers/retained issues and the next action; scripts/ledger supply counts, not a second handwritten report. Ordinary delivery ends at ready publish, which checks recovery dependencies; running recovery_argv is a separate rebuild, not another required smoke step. Coordinator-only maintenance trials follow the same rule unless a rebuild is explicitly assigned. Build from source plus saved state and keep artifacts in the source-stem folder.

Local extraction/rendering uses --workers auto or a positive integer. Machine-wide CPU/memory leases coordinate concurrent PDF jobs. Worker count and selection reasons appear in resource telemetry. Final PDF writing has one writer.

## Tool-session ownership and cleanup

Run scripts/coordination.py memory --task-dir TASK before a new batch of heavy tasks. Check again at stage changes or after a resource failure, not by continuous polling. Low memory queues new heavy work while existing jobs finish. Worker admission failures include available, reserved, estimated and coordinator RSS bytes; read those facts before retrying.

Before prepare, use the checked Python environment for repository coordination commands. After prepare, use the returned command_prefix with recovery/coordination.py for validation, memory and session commands too; plain system Python can lack the frozen dependencies. From the worker's own Node kernel directly launch `COMMAND_PREFIX recovery/coordination.py session-register --task-dir TASK --agent ACTUAL_ID`. It verifies kernel.js and its session ID in the caller's parent chain, and saves PID, start time, agent and memory under work/tool-sessions/. An unverifiable caller is reported, not guessed.

Before handing off: save edits, observations and a restart checkpoint; ensure live child jobs are registered with task_runtime; call session-mark --record RECORD --status cleanup_required --checkpoint FILE, then that worker's own js_reset when available. Keep the exact record path returned by session-register for the current kernel; never choose it by directory order or another agent's latest file. After a reset, register the new kernel when needed. Do not restart Node just to announce completion. If reset is unavailable, mark cleanup_unavailable and report it. Use a supported host close-agent operation only if one actually exists.

The coordinator runs sessions --task-dir TASK to observe whether the recorded PID/start identity disappeared; only a previously cleanup_required session becomes reset_observed. Completed, interrupted or closed agent labels alone are not cleanup evidence. Unknown kernels are listed separately and are never terminated by name, size or a guessed working directory. Confirm no unsupervised job remains before resetting a kernel; use task_runtime cancel only for its verified job tree. A whole-app restart is a last resort when the host cannot release a known idle session.
